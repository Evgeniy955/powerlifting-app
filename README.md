# IronLedger — Этап 0-3

Замена Excel-дневника тренировок по пауэрлифтингу. Next.js 14 + Prisma + PostgreSQL + Google OAuth.

## Что уже готово

- `prisma/schema.prisma` — модель данных: роли (Coach/Athlete), справочник упражнений
  с коэффициентами воздействия, 1ПМ по любому упражнению на атлета, циклы →
  микроциклы → тренировки → упражнения → подходы (динамический список).
- `prisma/seed.ts` — сидинг справочника упражнений (40 записей) и кривой коэффициентов
  усталости (100 точек), извлечённых из твоих файлов `03.08.26.xlsm` / `13.10.25.xlsm`.
- `src/lib/auth.ts` — Google OAuth через NextAuth, автоприсвоение роли Coach по email
  из `COACH_EMAILS`, остальным — роль Athlete с созданием профиля.
- `src/lib/metrics.ts` — реактивный расчёт метрик один в один с формулами из
  Excel: тоннаж, сред.вес, %1ПМ (Инт.Отн), КПШ, КО, индекс усталости (Инт.Фунт).
- Дизайн-токены под 3 темы (Dark Modern / Light Clean / Cyberpunk) в `globals.css`
  и `tailwind.config.ts`.

## Установка

```bash
npm install
cp .env.example .env
# заполнить DATABASE_URL, NEXTAUTH_SECRET, GOOGLE_CLIENT_ID/SECRET, COACH_EMAILS
```

## Google OAuth

1. console.cloud.google.com → APIs & Services → Credentials → OAuth Client ID
2. Тип: Web application
3. Authorized redirect URI: `http://localhost:3000/api/auth/callback/google`
4. Скопировать Client ID / Secret в `.env`

## Этап 1 (MVP дневника)

- `/workout/[id]` — экран тренировки: динамические подходы (+), реактивные метрики
  через `computeExerciseMetrics`, без автоподстановки следующего подхода
- `/athletes` — coach: список атлетов, добавление по email, автокомплит упражнений
  из `ExerciseCatalog`, привязка 1ПМ по любому упражнению
- `/cycles/[id]` — список недель/тренировок цикла + кнопка "Копировать последние
  2 недели" (видна и доступна только Coach, проверка также на сервере)

## Этап 3 (аналитика + экспорт/импорт Excel)

- `/athletes/[id]/analytics` — график прогресса (вес топ-сета + расчётный 1ПМ по
  Эпли) для любого упражнения с привязанным 1ПМ, гистограмма тоннажа/КПШ по неделям
- `GET /api/athletes/[id]/export` — скачивание читаемого .xlsx: лист на каждый
  цикл (дата, упражнение, подходы, тоннаж/КПШ/%1ПМ/КО/индекс усталости, заливка
  по зоне интенсивности, закреплённая шапка), плюс сводный лист по неделям
- `/athletes/[id]/import` — coach загружает .xlsx/.xlsm, видит предпросмотр
  распознанных/нераспознанных строк (сопоставление по названию упражнения из
  справочника) и подтверждает импорт в новый цикл; несовпавшие названия в БД не
  попадают — их нужно либо добавить в справочник, либо переименовать в файле
- Новая зависимость: `exceljs` (уже в `package.json`) — после обновления файлов
  выполни `npm install`

## Индекс усталости (ИУ / RPE)

Полностью заменил старую формулу из Excel-листа "F" на RPE-таблицу тренера
(Reactive Training Systems). `FatigueCoefficient` осталась в схеме неиспользуемой
(на случай отката), реально используется `RpeTable`.

- `prisma/seedRpeTable.ts` — оцифрованная таблица (повторы × ИУ → %1ПМ). Часть
  ячеек в исходнике пустая (низкие ИУ при малом числе повторов) — так и оставил,
  можешь дополнить файл вручную и перезапустить `npm run prisma:seed-rpe`.
- `src/lib/rpe.ts` — `estimateRpe()`: обратный поиск по таблице с интерполяцией
  (и по %1ПМ внутри колонки повторов, и между соседними колонками повторов, если
  точного числа повторов нет в таблице). Показывается напротив каждого подхода.
- `computeBlockFatigue()` — под каждым подходом свой ИУ (с накоплением), а общий
  индекс под упражнением — среднее по "рабочим" подходам:
  - тип тренировки определяется автоматически по максимальному рабочему весу в
    блоке: ≥80% от 1ПМ → тяжёлая/обычная, иначе лёгкая;
  - в среднее попадают только подходы ≥75% (тяжёлая/обычная тренировка) или ≥60%
    (лёгкая, с потолком индекса 7,5) — так разминочные/ступенчатые подходы по
    пути к рабочему весу не тянут среднее вниз;
  - у каждого подхода свой базовый ИУ по таблице (повторы + %1ПМ);
  - +0,25 к ИУ конкретного подхода за каждый следующий подход подряд при ≥85% в
    тяжёлой тренировке, и +0,25 за каждый следующий подход в серии из ≥4
    одинаковых по весу подходов ≥80% — берётся больший из двух бонусов, без
    задвоения.

```bash
npx prisma migrate dev --name add_rpe_table
npm run prisma:seed-rpe
```

## Этап 5 (AI-модуль)

Кнопка "Получить рекомендации" на странице аналитики (`/athletes/[id]/analytics`,
видна только тренеру). По клику собирается текстовая сводка по атлету — тоннаж/КПШ/
индекс усталости по последним неделям и прогресс расчётного 1ПМ по упражнениям с
заданным 1ПМ — и отправляется в Gemini API (`gemini-3.7-flash`) с системным промптом
тренера-ассистента. Модель отвечает 2-4 конкретными предложениями по следующему
микроциклу (снизить/увеличить нагрузку, разгрузочная неделя и т.п.) с обоснованием
по данным — без выдумывания цифр, которых нет в сводке.

- `src/lib/aiInsights.ts` — сборка сводки + вызов Gemini API
- `POST /api/athletes/[id]/ai-insights` — тренер-онли, проверяет владение атлетом
- `src/components/AiInsightsPanel.tsx` — кнопка + отображение ответа

Намеренно **не** авто-подставляет веса в план — это осознанный выбор MVP (тренер
читает рекомендацию и сам решает, что менять), а не автоматическая коррекция плана.
Дальше можно нарастить до авто-подсказки конкретных весов на следующую неделю, если
захочешь.

**Настройка:** добавь `GEMINI_API_KEY` в `.env` (ключ из Google AI Studio).
Без ключа кнопка покажет понятное сообщение вместо генерации рекомендаций —
остальное приложение при этом работает как обычно.

```bash
npm install   # подтягивает новую зависимость @google/genai
```

## Офлайн-режим — рассмотрели и отклонили

Приложение целиком построено на серверных компонентах Next.js (`middleware.ts` на
каждый переход дёргает `supabase.auth.getUser()`), так что открыть план без сети
можно только через service worker, кэширующий уже отрендеренные страницы/данные —
обычная навигация всегда требует сеть ещё до рендера. Технически это возможно и
дёшево по месту (JS-бандл ~1.9 МБ, один микроцикл — десятки КБ, год тренировок —
несколько МБ, в разы меньше стандартных браузерных квот), но узкое место не
память, а гарантия "неделя закэшируется сама, как только откроется атлету, даже
если телефон всё это время был офлайн" — это работает через Periodic Background
Sync/Push, а он есть только в Chrome на Android при установленном PWA и
отсутствует в Safari на iOS. Осознанно решили не делать: сложность (отдельный
слой кэширования + офлайн-рендер данных) не оправдана для платформы, где
гарантия всё равно неполная. Если понадобится вернуться — стартовать стоит с
простого MVP (network-first service worker на уже открытые страницы), не с
полного офлайн-слоя данных.
